# RLS, privileges and triggers: read-only audit of production (2026-10-18)

Project `ruibdsvrcctxgxctaxwe` (CareerAiHub), schema `public`. Method: read-only `SELECT`s through the Supabase CLI (`pg_class`, `pg_policies`, `pg_trigger`, `pg_proc`, `information_schema` grants and column privileges), exported and analysed with a script. Nothing was changed. Labels: **VERIFIED** (read from production on 2026-10-18) · **INFERRED** (follows from what was read, not tested) · **NOT READ**.
Companion: `docs/database/README.md` (what was applied), `docs/RUNBOOK.md`.

## 1. What was found

| 1 | **Every table has RLS on.** 34 objects in `public`: 32 tables and 2 views. No table without RLS. The two views are `security_invoker=true`. | `pg_class.relrowsecurity`, `reloptions` | Good | n/a |
| 2 | `ai_policies` and `trusted_issuers` have RLS on and **no policy**: nobody but `service_role` can touch them. Intended for `ai_policies`; for `trusted_issuers` the intent is INFERRED. | `pg_policy` count 0 | Good | no |
| 3 | **User tables are guarded by RLS only.** `anon` and `authenticated` hold table-level `INSERT/UPDATE/DELETE/SELECT/TRUNCATE/TRIGGER/REFERENCES` on 20 older tables (applications, candidate_trust_profiles, cover_letters, culture_leads, culture_quiz_events, employer_members, employers, insights, jd_analyses, job_listings, mock_sessions, negotiation_practice, pipeline_entries, profiles, resume_scans, star_stories, trust_matches, trust_messages, user_memory, waitlist). ## 2. What this changes in the risk register
- "RLS not in the repo, nothing proves isolation" becomes: RLS is on for every table, policies are per user or per verified employer member, and the sensitive columns are guarded by enabled triggers. The remaining gap is that no black-box test with the anon key and a user token has been run against these policies (**NOT READ / not tested**).
- "Three input tables accept browser-sent scores" is closed on production for `mock_sessions`, `star_stories`, `resume_scans`.
- The standing rule stays: no employer is verified until S3 is applied and tested, because finding 8 lets a verified employer read every visible profile.

## 3. Proposed hardening (PROPOSED, not applied, needs the owner's approval and a replica test)
1. Revoke from `anon` and `authenticated` the privileges no screen uses: `TRUNCATE`, `TRIGGER`, `REFERENCES` on the 20 tables in finding 3, and all privileges for `anon` on every table except the three public insert endpoints. Keep the privileges the app needs (`authenticated` SELECT/INSERT/UPDATE/DELETE as today). Check each table against the app first: `anon` must keep `INSERT` on `waitlist`, `culture_leads` and `culture_quiz_events`.
2. A trigger or column revoke for `profiles.is_pro` and `profiles.account_type`, before any feature reads them.
3. Apply S3 (consent-only access) with its test, then decide in writing which scores a recruiter may see (ADR-013), before the first employer is verified.
4. A black-box test: with a throwaway user, try to read and write another user's rows, set `verified_at`, set a score column and call the ledger functions, using the anon key and a user token; run it against a local replica first, then once against production with the owner's approval.

## 4. Not read
Storage buckets and their policies; realtime publications; the Auth settings (email confirmation, CAPTCHA, rate limits); `pg_graphql` exposure beyond the grants above; the bodies of the functions other than the six read; grants on the `auth` and `storage` schemas; any rate limit in front of the public inserts.
